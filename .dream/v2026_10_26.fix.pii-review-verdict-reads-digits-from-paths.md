# 🌙 dream: the pii.review verdict parser reads a blocker count off a file path

kind: fix · owner: transcriber · caught 2026-10-26

## .the cue that fired
the pre-commit gate blocked a clean commit: `🚨 anthropic/claude/opus — 5 blocker(s)`. the brain's own `output.response.json` read `"blockers": []` and its review read `no issues found`. one staged path was `.route/v2026_10_23.pr41-green/blocker/5.briefs.short.md`.

## .the gap, precisely
`pii.scan.via.brain.sh` takes the first match of `blockers?[^0-9a-z]{0,6}([0-9]+)` across the whole raw `rhx review` stdout. `blocker/5` matches: the `/` sits inside the punctuation gap. a path or filename with `blocker` (or `nitpick`) followed by a digit, printed before the summary, becomes the verdict. this is a false red, and a false green is equally possible (`blocker/0…` ahead of a real count).

## .the shape of the fix
1. parse only the summary block that `contract.reviewer-output` defines (the `└─ summary` lines), or read `output.response.json`'s array lengths from the review log dir, never the whole stdout
2. clamp: a raw stdout fixture whose scope lists `blocker/5.x.md` above a `0 blockers · 0 nitpicks` summary must parse as 0/0. a path with `blocker/0` above a `2 blockers` summary must parse as 2

## .why it is not done in this round
the order was one commit by 01:45 CT, and a parser change to the PII gate needs its own clamp and review. for that commit, the route file `blocker/5.briefs.short.md` (the cleared A/B escalation record) stays local and unstaged, so the false match never enters the scan.
