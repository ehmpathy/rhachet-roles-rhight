# 1.vision — the pii gate reads its verdict from the reviewer json

## the outcome world

**before.** the brain pass takes its blocker count from the first `blockers?[^0-9a-z]{0,6}([0-9]+)` match across raw `rhx review` stdout (`pii.scan.via.brain.sh:445`). any text `rhx review` echoes ahead of the summary competes with the summary. a staged path `blocker/5.briefs.short.md` reads as `5 blockers` and blocks a clean commit; `blocker/0…` ahead of a real `2 blockers` reads as 0 and **lets a leak through**.

**after.** the gate follows the `logs:` line — the one it already requires as the skip discriminator — to `<logs>/output.response.json`, and counts `.blockers | length` and `.nitpicks | length`. stdout carries no verdict. a json that is absent, unparseable, or whose fields are not arrays is a MALFUNCTION, and the gate blocks.

**the aha.** the registrator crew commits `.route/v2026_10_23.pr41-green/blocker/5.briefs.short.md` through the gate, untouched, and no human hears about it.

## the contract

inside `run_one_reviewer`, per attempt:

0. the review runs with `--polluters keep`, so route paperwork, dreams, and lockfiles stay in scope
1. no `logs:` line → unreadable (extant skip guard), retry
2. `logs=<path after the last "├─ logs: ">` (anchored on the tree glyph `rhx review` prints in its closing block); `json=$logs/output.response.json`
3. json absent or unparseable (`jq empty` fails) → unreadable, retry; misshaped (root not an object, or `.blockers` / `.nitpicks` absent or not an array) → unreadable, asked once, since a json written whole returns the same shape. with no `logs:` line, a refusal header (empty scope, overflow) names the cause and is asked once
4. `blockers=$(jq '.blockers|length')`, `nitpicks=$(jq '.nitpicks|length')` → `OK<TAB>b<TAB>n`

two unreadable attempts → `MALFUNCTION`, with the extant capped `whyfail` tail plus one cause line that names which read failed and the path it read: `no logs: line — the review skipped, or crashed before it wrote logs` · `no verdict json at <path>` · `verdict json unparseable at <path>` · `verdict json <fault per key>, at <path>` — the last names each absent or mistyped key and what it held (`.blockers is number, not an array`; `is null, not an object`), since a cause that names no key sends a human to hunt one that is present. a sharp path must teach its fix, and only the cause tells a locked keyrack from an upstream rename. the per-reviewer union in `main` is untouched.

## mental model

"the gate reads the reviewer's answer sheet, not the reviewer's chatter." the json is the machine verdict `rhx review` writes for exactly this purpose; stdout is a human summary.

## evaluation

- **solves the goal**: both failure directions close, because no stdout text reaches the count.
- **pros**: one source of truth; the regex and its markdown-gap caveats (`:430–444`) delete outright; a count no reviewer prose can shift.
- **cons**: a new coupling to bhrain's artifact name `output.response.json` (`asRunArtifactPath.js`, `NAME_OF_RUN_ARTIFACT.response`) and to the json field names. a rename upstream fails **closed** (C8, C10), loud, never open.
- **edge cases**: see the forbidden rows in the inventory — no cell lets an unread verdict pass.

## open questions & assumptions

- **[answered]** is the `logs:` path resolvable from the gate? yes. it is relative to the cwd `rhx review` ran in (`setReviewLaneOutcome.js:62` `path.relative(input.cwd, input.logDir)`; `contract/cli/review.js:609` `cwd = process.cwd()`), and the gate never `cd`s. an absolute path also works unchanged.
- **[answered]** is `.blockers | length` the same number `rhx review` reports? yes. one object is both the json and the summary source (`stepReviewOfCompiled.js:194–205`).
- **[answered]** can a failed run leave a json that reads clean? no. only `setOutputArtifacts` writes it, after the brain answered (`stepReviewOfCompiled.js:196`).
- **[answered]** do parallel reviewers share a json? no. each log dir is `<iso-ms>.<pid>.<uuid>` (`genLogDirName.js`).
- **[answered]** "batched runs union per batch, as today": the gate has no batch loop, and `rhx review` cannot split under the gate. it splits only on declared partitions, and the gate passes no `--partition` and writes `--output` to a temp path with no route identity (`getAllPartitionFlagsOfReviewRun.js` returns `[]`). so one run writes one json, and the extant union across `--brain` reviewers (`main`) stays as is. ⚠️ a future `--partition` on the gate would print several log dirs; this contract reads the last only, and would need a per-partition union.
- **[answered]** does any caller re-parse a count off stdout? no. `pii.scan.sh` and `.husky/check.pii.sh` act only on the brain skill's exit code (`pii.scan.sh:214–231`; `check.pii.sh:102–144`). the fix stays inside `run_one_reviewer`.
- **[answered]** is `jq` on the host? sibling skills already call it (`transcribe.pdf.sh`, `patent.priors.search.sh`, `briefs.integrity.sh`). if absent, `validate()` blocks at exit 1 with `jq not found`, before any review runs — closed, and under its true cause.
- **[wisher]** none open. the cause line in the malfunction report (see contract) is an addition beyond the wish, kept to four fixed cause shapes; veto it at approval if unwanted.
- **[research]** none.

## what is awkward?

- the skip guard and the json read both hang off the `logs:` line. that is right (one discriminator), but a `logs:` line that ever lands inside a staged path is a second-order version of this same defect. mitigated: take the **last** `logs:` line, which `rhx review` prints in its closing summary.
- the gate now trusts an artifact path chosen upstream. a fail-closed rename is the right failure, but it would block every commit in the org until a fix ships.
